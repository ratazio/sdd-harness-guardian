Execution — draft is not authorization

Mission: show how each material task creates a safe, observable increment. For each source task, project its non-empty objective/outcome/increment, scope/anti-scope, contracts, dependency, risk/assurance, validation/evidence, exit, status/authority and why-now—not only a title.

Task ledger and cards

State status, dependency, validation, evidence and limits. A task may be discovery, operations or delivery; do not invent files or implementation where the canonical task has none.

Validation

Mission: make the proof path and its limits recoverable. Map acceptance/risk to method, command or manual context, fixture/data when relevant, oracle, evidence destination, owner and honest limitation/skip rationale.

Commands and limits

A command is not universal. A source-backed manual or non-software check may be concise, but it must still make method, context, oracle, evidence and residual limitation recoverable. Structural validation does not prove semantic usefulness.

Evolution and state

Mission: explain what changed, why, what remains open and what gate is truthful now. Render material decisions, supersession, freshness, checkpoint, risks and authority rather than inferring state from prose.

Gates

Show truthful state and open risk. Missing authority or a gate that affects the next action is an owned material question.

Decision and next step

Mission: make owner, consequence, authorization boundary and one exact next action unambiguous. The HTML displays canonical authority; it never grants approval itself.

Append meeting decision and propagate sources before refresh.
