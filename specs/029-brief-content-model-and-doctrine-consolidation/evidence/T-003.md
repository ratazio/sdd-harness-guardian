### 3. Janela de falso-negativo na detecção de duplicidade (registrada, não corrigida)

A assinatura de duplicidade em `validate_brief_model.py` é
`(frozenset(node_ids), frozenset((from, to, label, state)))`. Isso significa
que dois grafos idênticos em nós/arestas mas com um **rótulo** ou **estado**
diferente numa aresta **não são detectados** como duplicados. Essa escolha é
defensável e bate com a letra de AC-004 ("mesmo conjunto de nós/arestas"): um
grafo que evolui de `proposed` para `preserved` entre revisões é progressão
legítima do mesmo relacionamento, não uma cópia acidental, e não deveria
disparar o check.

O limite consciente: **se o defeito de origem relatado pela spec 028 tiver
sido um copy-paste com o rótulo de uma aresta trocado** (não apenas um zoom
idêntico byte a byte), essa janela deixa passar exatamente esse caso. Não
foi corrigido nesta revisão porque (a) o prompt da revisão pediu para não
mudar código, e (b) apertar a assinatura para ignorar `label`/`state` teria o
efeito oposto: um grafo que genuinamente evoluiu o estado de uma aresta
passaria a ser falso-positivo, o que é pior para o fluxo comum. Registrado
aqui como decisão consciente, não acidente — se uma instância futura de
duplicidade-por-rótulo-trocado for observada, o ajuste é estreitar a
assinatura para ignorar `label` (manter `state`, que é o campo com
significado editorial) e cobrir com um teste que reproduza o caso real, não
generalizar preventivamente sem um caso.

## FR-004 / AC-004 — SVG acessível a partir de nós/arestas

`_render_relation_svg(graph, aria_label)` (scripts/project_brief.py) gera:

- `<svg role="img" ... aria-label="...">` com `aria-label` não vazio
  (rótulo do grafo ou seu id) **e** `<title>` dentro do SVG — as duas vias
  que AC-004 aceita, presentes simultaneamente;
- `data-architecture-text-equivalent="..."` no `<div class="diagram">` que
  envolve o SVG, com o texto de `_relation_text_equivalent(graph)`: lista
  todo nó (`id (label)`) e toda aresta (`from -> to: label [state]`) — nunca
  vazio para um grafo schema-válido (`nodes` tem `minItems: 1`);
- um parágrafo visível (`.brief-relation-text-equivalent`) com o mesmo texto,
  não só o atributo `data`;
- uma legenda de texto visível (`.brief-relation-state-legend`) listando os
  quatro estados **por nome** (`proposed; preserved; out-of-scope; discovery`)
  — nunca só a cor da linha da aresta.

Coberto por `scripts/test_brief_forms.py`:
`test_topology_block_renders_svg_with_role_img_and_nonempty_aria_label`,
`test_topology_block_carries_nonempty_text_equivalent`,
`test_topology_legend_states_are_visible_text_not_only_color`,
`test_sequence_block_reuses_the_same_accessible_svg_mechanism`.

`sequence` reusa o mesmo `_relation_graph_html`/`_render_relation_svg` —
mesma garantia de acessibilidade, sem uma segunda implementação de diagrama
para manter sincronizada (NG-003).

## FR-004 — detecção de topologia duplicada

Implementada em `scripts/validate_brief_model.py::_semantic_errors`, não em
`project_brief.py`: é uma checagem de consistência do **modelo**
(`relations[]`), e `project()` já chama `validate_model(model)` antes de
projetar, então a detecção bloqueia a projeção de graça, sem código extra em
`project_brief.py`.

Algoritmo: para cada grafo declarado em `relations[]` com pelo menos dois
nós, calcula uma assinatura = `(frozenset(node_ids), frozenset((from, to,
label, state) por aresta))`. Dois ids de grafo **distintos** com a mesma
assinatura são reportados como "duplicate topology", nomeando os dois ids.
É diff de conjunto, não comparação de nome — renomear um grafo sozinho nunca
dispara (`test_renaming_a_graph_alone_is_not_a_duplicate`), e copiar um grafo
sob um id novo sempre dispara
(`test_duplicate_relation_graphs_are_detected_and_reported`,
`test_duplicate_relation_graphs_block_projection`).

Fixture negativa:
`scripts/fixtures/project-brief/forms/model-duplicate-topology.yaml`
(`graph-a`/`graph-b`, nós e arestas idênticos, ids e rótulos diferentes).

Este é exatamente o defeito relatado pela spec 028 ("a mesma topologia em
zooms distintos"), agora detectável por diff de conjuntos em vez de
inspeção humana.

## Fechamento de IR-003 — fixture sintética não-software

Todos os oito mocks em `testes/mock-runs/` são `domain: software`
(confirmado por leitura — nenhum mock declara `domain` diferente porque o
conceito de `domain` só existe a partir do schema de T-001). IR-003 não podia
ser fechado com o material existente. Construída:
`scripts/fixtures/project-brief/non-software/` — uma iniciativa sintética
`domain: docs`, `profile: minimal` (migração de taxonomia de uma base de
conhecimento de suporte: sem código, sem serviço, sem deploy), com
`spec.md`/`decision-log.md`/`run-state.yaml` plausíveis e um `brief-model.yaml`
válido (`validate_brief_model.validate()` retorna `[]` —
`test_minimal_docs_model_is_schema_valid`) que projeta com sucesso.

### O que a fixture revelou (achados, não ajustes forçados)

1. **`topology` genuinely não se aplica.** Uma migração de taxonomia de
   documentação não tem relação espacial/estrutural material — não há
   "arquitetura". A fixture não usa `topology` nenhuma vez
   (`test_non_software_fixture_exercises_multiple_forms_without_topology`),
   e isso é o ponto: FR-005 existe exatamente para que uma rota/forma sem
   base material simplesmente não apareça, sem exigir uma disposição
   `not_applicable` forçada só para preencher um catálogo.
2. **`sequence` generaliza bem além de "diagrama de arquitetura".** O ciclo
   de vida de um redirecionamento de URL (`old -> redirect (6 meses) -> new`)
   é uma relação material genuína, não menos real por não ser código. O
   mesmo `_render_relation_svg`/grafo de nós-arestas construído para zooms de
   arquitetura funcionou sem alteração nenhuma
   (`test_non_software_sequence_block_still_produces_accessible_svg`). Isso
   é evidência de que o modelo de relação (FR-004) não foi otimizado para
   topologia de software especificamente — é genuinamente um modelo de
   grafo com rótulo/estado, e "arquitetura" é só um dos usos.
3. **`ALLOWED_BLOCK_SOURCES` é uma lista de nomes de arquivo com cara de
   SDD, fixa independente de domínio — e isso NÃO foi corrigido aqui.**
   `scripts/project_brief.py:ALLOWED_BLOCK_SOURCES` (via
   `brief_v2_sources.V2_REQUIRED_SOURCES`) só aceita
   `spec.md`/`impact-map.md`/`plan.md`/`tasks.md`/`validation-plan.md`/
   `decision-log.md`/`progress.md`/`run-state.yaml`/`ratchet.md`. A fixture
   `non-software` teve que inventar um `run-state.yaml` com uma chave
   `quality_gates` só para ter uma âncora `not_applicable` — algo que uma
   equipe de documentação genuinamente não-SDD nunca produziria
   organicamente. **Isto é o achado que o prompt do orquestrador pediu para
   registrar em vez de forçar a caber**: o vocabulário de fontes do
   projetor pressupõe que toda iniciativa é governada por este harness SDD,
   mesmo quando `domain` diz explicitamente que não é código. Não é um bug
   de T-003 (a lista é FR-002/T-002, closed by design, para impedir que um
   agente cite uma fonte arbitrária) — é uma tensão estrutural entre FR-005
   (domínio livre) e a inventário de fontes fixo, que nenhuma task da 029
   assume corrigir. Registrado aqui para uma task futura decidir se o
   inventário de fontes deveria ser parametrizável por domínio ou se
   "toda iniciativa que usa este projetor é, por definição, uma iniciativa
   SDD" é a resposta aceita (e nesse caso `domain: docs/policy/ops/research`
